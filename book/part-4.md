# PART IV — 4:26 AM

## 21. Deployed, Technically

There's a particular flavor of despair reserved for the moment a deployment finishes successfully — green checkmark, no errors, pipeline complete, every box the CI system knows how to check has been checked — and the site it produced is broken anyway. Not broken in a way that shows up in a log. Broken in a way you only find by actually opening the URL, the way a restaurant can pass every health inspection and still serve you something inedible.

He opens the URL. The page loads, in the sense that HTML arrives and a browser renders it. What it renders is a skeleton with no skin: unstyled text stacked in the default serif the browser falls back to when it can't find the stylesheet it was told to load, a scatter of broken image icons where the hero illustration should be, a layout that looks less like a portfolio and more like a ransom note assembled from whatever fonts happened to be lying around. Every asset the page needs — the CSS, the fonts, the images — is returning a 404, cheerfully, as if being asked for something that obviously doesn't exist.

It exists. That's the maddening part. It exists exactly where it's supposed to exist on his own machine, where `npm run dev` has been serving this exact page correctly for weeks. The problem, once he's spent twenty minutes ruling out everything else, turns out to be a single, almost insultingly small fact about how GitHub Pages actually serves a site: it doesn't live at the root of a domain the way his local dev server pretends it does. It lives in a subdirectory, named after the repository — `/Portfolio/`, in his case, capital P and all — and every asset reference his build had generated assumed it would be served from the root, from `/`, because that's the only reality the local dev server had ever shown it.

Locally: fine. Every path resolves, every stylesheet loads, because locally there is no subdirectory, there's just `localhost:3000` pretending to be the whole internet. The moment the exact same build gets deployed somewhere that isn't the root of its own domain, every one of those absolute paths becomes a lie. The browser asks for `/globals.css`. The actual file lives at `/Portfolio/globals.css`. Nobody told the browser about the extra folder, because nothing in the build process knew about it either — it had been trained, entirely correctly, on an environment where the folder didn't exist.

The fix, once he finds the right paragraph of the right documentation page, is one configuration value: `basePath`, set to `/Portfolio`, telling the framework, once and for all, that every asset it generates needs that prefix baked in from the start. One line in a config file. A problem that took most of an hour to diagnose, solved by a setting that had apparently been sitting in the framework's documentation the entire time, waiting for him to need it badly enough to go looking.

He commits it. `Fix: Set basePath to /Portfolio for GitHub Pages asset loading` — a commit message with no adjectives in it, no relief visible in the text, which is its own kind of tell. The messages that sound the calmest are usually the ones written right after the least calm hour.

He pushes. The deploy kicks off. He watches the little yellow dot in GitHub's Actions tab turn, eventually, green, and refreshes the live URL with the specific bracing posture of someone who has been burned by a green checkmark exactly one hour ago and does not entirely trust it this time either.

It loads. Styled, correctly, images in place, fonts rendering the way they're supposed to. He does not celebrate this the way the RL agent's first improving reward curve got celebrated, or the way the ring redrawing itself got celebrated. There's no thrill in fixing a bug that was never interesting to begin with — just a config value nobody warns you about until it's already cost you an hour. What there is, instead, is the much quieter, much less photogenic feeling of a slightly clenched jaw finally unclenching. Not joy. Relief with the volume turned all the way down.

## 22. Everyone's Node Is a Different Node

The email arrives — not an email exactly, a GitHub Actions notification, red, unambiguous, the kind of failure that at least has the decency to fail loudly instead of quietly serving broken assets. The build step has failed. Not his code. The build step itself, before his code even gets evaluated, on a line that says, more or less, that the version of Node.js the workflow is running doesn't meet the minimum the framework requires.

This is, on some level, a completely reasonable thing for software to enforce. Frameworks evolve. They use newer language features, newer APIs, and at some point they simply stop supporting whatever version of the runtime came out three years ago, because supporting everything forever is how you end up maintaining three parallel realities at once. He understands the reasoning. Understanding the reasoning does not make it any less irritating, at close to midnight, to discover that the exact same code that runs perfectly on his own machine — where Node updates itself quietly, in the background, without asking his permission or his opinion — fails on a CI runner that's frozen at whatever version somebody configured, possibly years ago, possibly by a workflow template he copy-pasted from a tutorial without reading closely enough.

He checks his local version first, out of habit more than logic, because the actual bug is never in the place you check first out of habit. Local: fine, current, more than sufficient. The problem lives entirely in a YAML file he wrote once and hasn't looked at since, a `.github/workflows/deploy.yml` that specifies, explicitly, in a `node-version` field, a number that made sense the day he wrote it and has been quietly aging out of relevance ever since, invisible, because nothing about a correctly running workflow prompts you to go back and check whether its assumptions are still true.

This is a particular, underrated category of bug: the one where nothing is actually wrong with anything you're currently looking at. The code is fine. The config, at the time it was written, was fine. The only thing that changed is time itself, silently, elsewhere, in a dependency's release notes he never read because reading every dependency's release notes is a full-time job he does not have. `Fix: Update Node.js version to 22 for GitHub Actions.` One number, bumped. A problem that has nothing to do with cleverness and everything to do with the unglamorous, ongoing tax of maintaining anything that depends on anything else, which is to say: everything.

He half-expects this to be the end of it. It is not the end of it.

## 23. The Lockfile Argument

`npm install` fails next, and it fails with a message dense enough that reading it in full at this hour feels less like debugging and more like being shouted at in a language he technically speaks but is too tired to parse at native speed — a wall of text about peer dependency conflicts, one package wanting a version of React that another package refuses to coexist with, an entire dependency tree arguing with itself in front of him, politely, in red text, without offering to settle the argument on its own.

There is a flag for this. There is, in fact, more than one flag for this, and the difference between them matters more than their names suggest. `--legacy-peer-deps` tells npm to go back to how it used to resolve these conflicts before it started being strict about them — permissive, forgiving, willing to install things that technically disagree with each other and hope, quietly, that the disagreement never actually matters at runtime. `--force` is the blunter instrument, the one that skips the argument entirely and installs what you asked for regardless of what anything says it wants, consequences unexamined, a flag whose name is doing you the favor of being completely honest about what it's about to do.

He tries the gentler one first, because trying the gentler flag first is a matter of professional self-respect, a small ritual of due diligence before reaching for the sledgehammer. It works, for a while — locally, on his own machine, `--legacy-peer-deps` resolves the argument well enough that the dev server starts and the site renders and nothing looks obviously wrong. He commits the lockfile it produces, pushes, and the CI runner, working from a marginally different environment, with its own cached state and its own subtly different resolution order, rejects it anyway, citing a conflict the local install had somehow tiptoed around without incident.

This is the specific, low-grade indignity of frontend tooling in this era: the same command, given the same instructions, on two machines that are supposed to be equivalent, can produce two different outcomes, and there is no clean, satisfying explanation for why beyond "caches are different, timing is different, the exact order packages got resolved in was different, and somewhere in that difference a conflict that stayed dormant on one machine woke up on the other." It's not a bug you fix. It's a bug you route around.

`Use npm install --force to bypass package-lock conflicts.` The commit message that finally gets the CI runner to cooperate, and it is, if he's honest, not a message he's proud of. `--force` is a flag that works by refusing to ask the question the dependency resolver exists to ask. It's the software equivalent of two people arguing loudly in a doorway and a third person just walking straight through the middle of them, ignoring the argument entirely, on the theory that whatever they're disagreeing about probably doesn't matter to anyone but them.

Sometimes it doesn't matter. The site works. Nothing visibly breaks. And there is, sitting underneath the relief of a green build, a small, specific unease that never fully resolves — the awareness that he skipped past a warning instead of understanding it, and that skipping past a warning is exactly the kind of decision that looks fine for months and then, on some unlucky future Tuesday, turns out to have been the reason something quietly broke three layers downstream of where anyone thought to look.

He doesn't go back and fix it properly that night. He notes it — mentally, not even in a comment, which is its own small confession — as a thing to revisit eventually, filed in the same drawer as every other "eventually" he's ever opened a ticket for in his own head and never actually gotten back to.

## 24. Trigger Fresh Deployment

There are two commits in the history, weeks apart, that say almost exactly the same thing: `Trigger fresh Pages deployment.` Nothing else changed in either commit. No code was different. The entire content of each change is an empty gesture — a whitespace edit, most likely, or a comment nudged one line, made for the sole purpose of giving GitHub something new to build, because the previous deployment had gotten stuck in a state that nothing short of a fresh trigger seemed able to unstick.

This is one of the more quietly demoralizing categories of problem in software: the one with no reproducible cause, no error message pointing anywhere useful, and a fix that isn't really a fix so much as a shrug formalized into a git commit. Something, somewhere in GitHub's deployment pipeline, got wedged — a cache that didn't invalidate, a build artifact from three commits ago that the system kept serving instead of the current one, a timeout that quietly expired without telling anyone it had expired. He never fully diagnoses it. He doesn't have access to diagnose it; the failure lives inside infrastructure he doesn't control, on the other side of an API he can only poke at from the outside, and at some point continuing to investigate costs more than just doing the thing that's historically worked.

So: an empty commit. `Trigger fresh Pages deployment.` It is, in its own small way, an admission — not of defeat, exactly, but of a kind of practical humility that took longer to arrive at than it should have. Not every problem yields to understanding it fully. Some problems yield to poking the system and hoping the poke lands somewhere useful, and there's a version of professional pride that resists this, that wants every fix to be traceable to a cause, and there's a version of 1 a.m. pragmatism that has stopped caring whether the fix is intellectually satisfying as long as the site comes back up.

A related commit, around the same stretch of the log, bumps the deploy timeout to thirty minutes — `Increase Pages deploy timeout to 30 minutes` — which is its own quiet confession. Something in the build had started taking long enough that the platform's default patience ran out before the job finished, and rather than figure out why the build had gotten slower, the actual fix was to ask the platform to be more patient. Not every problem needs solving at its root. Some just need enough slack that they stop being problems in practice, even while remaining, technically, unexplained.

He is aware, writing this kind of fix, that it wouldn't survive a code review at a company with stricter standards than a personal portfolio has. Nobody reviews these commits but him. That's both the freedom and the risk of a project with an audience of one — you can ship the shrug, because there's no one downstream of you who's going to ask why the timeout got bumped instead of the underlying slowness getting investigated. Nobody's going to ask. He's the only one who was ever going to.

## 25. What Looked Brilliant at Midnight

Every so often, a redesign survives the night it was built in and dies the next morning, in daylight, on a second monitor, viewed with eyes that slept in between — and the gap between how it looked at 1 a.m. and how it looks at 8 a.m. is not subtle. It's not a small adjustment waiting to happen. It's the uncomfortable discovery that an entire evening's worth of confident decisions were made by a version of himself whose taste had quietly degraded somewhere around hour four, without any warning that it was happening in real time.

This isn't a story about one specific redesign. It's a pattern that's repeated enough times across enough different projects that he's stopped being surprised by it and started, instead, simply expecting it — a tax he now budgets for, the way you budget for a dependency update you know is coming even before you know exactly what it'll break. Something about the particular hour — the tiredness, the isolation, the total absence of any other opinion in the room to push back against his own — makes certain decisions feel obviously correct that turn out, in daylight, to be merely the loudest idea that occurred to him at the time.

A color that read as "confident and warm" at midnight reads, the next morning, as slightly too saturated, a little aggressive, the visual equivalent of someone talking too enthusiastically too early. A layout decision that felt, in the moment, like a bold departure from convention reveals itself, with a clearer head, to be simply confusing — not bold, just wrong, the difference between the two invisible from inside the hour that produced it and completely obvious from outside it.

He has a theory about why this happens, unverified, untested, built entirely out of his own repeated experience rather than anything he read: that late at night, with nobody around to react to a decision in real time, the internal feedback loop that normally tempers a choice — the flinch you'd feel if a colleague raised an eyebrow, the small social calibration that happens automatically when another person is in the room — goes quiet. Not gone. Just quiet enough that a bad idea gets to run further before anything catches it. Alone, at 1 a.m., an idea can sprint for hours without ever encountering the friction that would have slowed it down at 2 p.m. in an office.

The practical response, arrived at gradually over enough of these mornings, isn't to stop building at night. That was never actually on the table — the night is when the freedom lives, when there's no meeting to interrupt the thread, and giving that up would solve the problem by removing the thing that makes the problem worth having. The response, instead, is smaller and less dramatic: never ship straight from the hour that built it. Sleep on it. Look again with the specific, slightly betrayed clarity of a morning brain reviewing a midnight brain's homework, and trust that verdict over the one that felt so certain eight hours earlier.

It's not a perfect system. Some midnight decisions survive the morning review completely intact, vindicated, correct after all — the terracotta accent color, as it happens, is one of them, unchanged since the night he picked it, still there in the token file exactly as it was the night it felt obviously right and turned out, upon reinspection, to actually be obviously right. But he no longer trusts that outcome by default. He checks. Every time. Because the alternative is shipping four commits of confident 1 a.m. certainty and discovering, days later, that an entire visual language got built on top of a decision that never should have survived past sunrise.

## 26. Persistence, or Just Refusing to Admit It

There's a version of this same night — not tonight specifically, but any of the nights this book keeps drawing from — where the honest ending isn't a fix. It's a decision to stop, made not because the problem got solved but because continuing had stopped being persistence and started being something closer to refusing to admit a mistake.

The line between the two is genuinely hard to see from inside it, and he has, by now, been on both sides of it often enough to know that the feeling accompanying each is nearly identical. Persistence feels like: I am close, I can see the shape of the fix even if I haven't found it yet, one more attempt is going to land. Refusing to admit it feels, from the inside, like exactly the same sentence. The tell isn't in how it feels. It's in what's actually changing between attempts.

Real persistence looks like narrowing — each failed attempt eliminates a possibility, and the space of what could still be wrong gets visibly smaller with every pass, even if the fix itself hasn't arrived yet. He can point to it, on the nights it's real: an hour ago the bug could have been in four places, now it's down to one, the debugging is converging even though the answer isn't in hand yet.

The other thing — the thing that only reveals its true name in hindsight — looks like repetition dressed up as narrowing. The same three things, tried again, slightly reordered, on the theory that maybe this time the universe will resolve the coin flip differently. No new information gathered between attempts. No hypothesis actually eliminated. Just the same four moves, run in a different sequence, because stopping feels like losing and trying again, however unfounded, still feels like progress.

He has a rough personal rule for catching this, developed the hard way, applied imperfectly: if the last three attempts haven't changed what he knows about the problem — not the outcome, the knowledge, whether he's eliminated a possibility or just repeated one — it's time to stop and either ask someone or sleep on it, because a fourth identical attempt is not persistence. It's superstition wearing persistence's clothes.

The RL agent's discount factor bug, hours earlier, was genuine persistence — each failed run did teach him something, even the ones that didn't fix anything, because each one ruled a possibility out. The ScrollTrigger bug was the same, technically, though it took an embarrassingly long time to admit the first hour of it had taught him nothing at all and the actual narrowing only started once he stopped guessing and went looking for someone else's account of the same failure.

There's no clean lesson here, and he's suspicious, by now, of any account of a debugging night that produces one. Some nights the persistence pays off exactly when it should. Some nights it doesn't, and the correct move — the one that actually respects the work, rather than the one that feels like respecting it — is closing the laptop with the bug still unsolved, which is its own kind of discipline, harder to perform and much less satisfying to describe than the version where everything gets fixed by 2 a.m. and the story has a tidy shape.

Most nights don't have a tidy shape. This is one of the ones this book is going to let stay that way.
